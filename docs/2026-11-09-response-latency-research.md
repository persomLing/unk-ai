**UNK AI 回答延迟调研 · 2026-11-09**

> 本文保留改造前的调研证据与流程。普通问答现已接入模型工具循环，当前实现和验证请看[模型驱动检索交付说明](2026-11-09-model-driven-research.md)。

结论：存在明确的优化空间，优先减少主回答之前的模型往返和重复、串行抓取。现有证据还不能把用户这次近一分钟的等待准确分摊给各个环节，也不能保证优化后一定达到元宝的 8 秒。

真实对照记录的匿名化问题摘要为“比较两支参赛队伍的夺冠概率和对位实力”：使用兼容中转/聚合服务、默认思考设置时，UNK AI 约一分钟，元宝约 8 秒。公开记录省略原提问和部署专用模型别名，未核实中转方实际模型版本。两边的比赛背景、模型、思考预算、答案长度、首字/完成计时口径及本页开关尚未核实。

本次完成当前生产代码审计、真实服务组合的本地替身探针、相关行为测试和官方公开资料核验。未调用用户的真实模型服务，未修改生产代码。

**整体编排：前置资料准备与模型工具循环**

当前普通问答采用前置资料流水线：按开关和规则准备本页 → 本地策略或独立模型判断是否联网 → 程序决定搜索查询、来源抓取 → 将资料交给主模型思考和回答。联网判断只消费 `search` 布尔值，其 `reason` 和模型思考都不进入主回答上下文。主回答请求没有声明 tools，也没有处理工具调用、回填结果后再次生成的循环。

因此，界面先出现“判断联网/读取资料”，然后才出现主回答的思考，是当前执行顺序的直接反映。判断请求与主回答即使用同一个模型，也不是一次连续的分析过程。

另一种通用编排是：问题和可用工具一起交给模型 → 模型分析后直接回答或请求工具 → 程序校验并执行 → 将工具结果放回同一逻辑回合 → 模型继续分析，必要时再调用工具 → 完成回答。一个逻辑回合可能包含多次 HTTP 请求；思考状态如何延续取决于供应商协议，不能只复用 runId 就声称复用了内部推理。产品界面的“思考”标签也不能单独证明其后台采用哪种实现。

本项目的页面 Agent 已有独立的“决策→浏览器执行→再观察/决策”循环，但普通联网问答尚未接入此能力。演进方向可是在普通回合中增加受控的只读检索工具循环，让模型统一决定何时搜索、读哪个来源、何时资料足够，而不是不断增加主题关键词规则。用户明确要求的必要页面资料仍由确定性规则保证，权限、目标、取消、预算和唯一主回复继续由程序控制。

这种演进能省去独立分类并减少不必要的预读，也能让模型按缺口补查；但多轮搜索可能比当前流程更慢，必须限制轮数、并发、资料量和总时间，并区分快速回答与深入研究。主题规则优化仅为局部减负措施，不是整体编排方案。

**这句问题实际走什么流程**

对原句直接运行当前 `webResearchPolicy`，无论是否有可用页面正文，结果均为 `auto`。它没有命中现有时效、易变事实、具体版本或明确搜索规则，先交给同一模型判断是否检索。`researchQueries` 对原句只生成一个查询，不能把这次慢说成“必然进行了三轮搜索”。

在关闭本页、无需历史压缩、判断返回需要搜索、搜索返回三篇独立来源、开启正文抓取的可控条件下，真实 ChatService / TurnRunner / Repository / ModelGateway / WebResearcher 组合执行了：

```mermaid
flowchart LR
  A[联网判断：同一模型、非流式] --> B[联网搜索]
  B --> C[抓取正文 1]
  C --> D[抓取正文 2]
  D --> E[抓取正文 3]
  E --> F[主模型思考与流式回答]
  F --> G[回答完成后生成建议问题]
```

主回答前有五次服务请求；加上主回答共六次。其中联网判断和主回答是模型文本生成，搜索和抓取是独立工具接口，不是六次主模型回答。接口内部实现及中转方等待情况未知。建议问题发生在主回复成功之后，不计入其关键路径。

**页面读取是否拖慢了这个例子**

页面模式开启时，每轮都会 fresh 读取当前正文并加入上下文。因此在无关网页上问独立赛事问题，可能多出读取及无关输入成本；关闭“基于当前页”不会关闭全网搜索。

但不能把所有页面能力都算到这句话上。用原句和模拟完整正文运行现有策略，补读判断模型调用为 0、深读为 0，视觉预检查不触发、接口监听不推荐。真实页面若存在资料缺口，行为仍可能不同。

| 条件性环节 | 当前行为 | 本例适用边界 |
| --- | --- | --- |
| 页面基础读取 | 页面开关开启则必读；本页正文和需要的站内目录已有并行 | 本次开关和页面内容未知 |
| 智能补读 | 灰色缺口最多一次 8 秒判断，判断与结构读取共同 16 秒预算 | 完整正文探针未触发 |
| 接口采集 | 需要且已获本站许可时监听 3 秒，已有严格身份约束的 5 分钟内存缓存 | 本例策略未推荐 |
| 视觉判断 | 视觉意图、页面已读、无用户图片等条件满足后才判断 | 本例策略未触发 |
| 历史压缩 | 达上下文预算 90% 且估算至少 8000 tokens 才触发，串行等摘要 | 新短会话不触发，长对话可能显著增加延迟 |
| 必要保存 | 保留浏览器 outbox 提交；现有目录同步另有最多 1.5 秒等待 | 值得优化，但通常不能单独解释一分钟 |

对应生产入口见 [conversation-service.js:414](../src/app/conversation-service.js#L414)、[adaptive-reading.js:230](../src/sidepanel/features/page-reading/adaptive-reading.js#L230)、[auto-visual-slot.js:64](../src/sidepanel/features/visual-context/auto-visual-slot.js#L64)、[context-service.js:39](../src/app/context-service.js#L39)、[conversation-store.js:132](../src/utils/conversation-store.js#L132)。表中的预算不是平均耗时，嵌套超时不能简单相加。

**建议先做的一批优化**

| 优先级 | 改动 | 可预期的结构收益 | 必须保持的行为 |
| --- | --- | --- | --- |
| P0 | 搜索已有合格正文时复用，只抓缺失、截断或必要待核实的来源 | 三篇均可用时省去三次抓取 | 检查来源、完整度和时效；摘要继续标为摘要，不能冒充已读正文 |
| P0 | 网关正文改为最多 2–3 个有界并发，并接通统一取消/截止信号 | 三篇抓取由 `T1+T2+T3` 缩短到接近 `max(T1,T2,T3)`（并发 3、无争用时） | 结果保持确定顺序和来源归属；停止后不发新请求、不启动迟到主回答 |
| P1 | 对明确的当前赛事预测/实时阵容实力问题直接检索，对稳定知识增加高置信本地跳过 | 省一次联网判断；不应只硬编码 BLG/GEN 两个队名 | 历史比赛、未知赛事和混合问题单独处理，不泛化成“出现比赛一律搜索” |
| P1 | 联网/阅读/视觉判断独立配置经过能力确认的非思考或低推理策略 | 降低剩余辅助请求等待；用户主回答思考设置保持独立 | 根据具体服务文档适配参数；不支持时有明确降级，不假装已关闭思考 |
| P2 | 明确要搜索的问题，可与独立的准备工作并行，在主回答前汇合 | 隐藏可重叠的等待 | 固定同一问题、会话、模型快照和取消信号；必要证据失败仍报错 |
| P2 | 为支持的服务接入原生搜索回答协议，提供快速/深入两种策略 | 减少客户端往返，并按需求控制检索深度 | 通过 ModelGateway 显式能力适配，保留引用、唯一主回复和流式错误语义 |

这批改动应主要落在 `features/web-research/` 和模型参数适配边界。若修改 ChatService 或 llm-client，应先补能复现当前问题的组合/协议回归，再做最小修改；无需为此重写发送、队列、重试或 Agent 主循环。

原生搜索是后续适配方案，当前没有直接接入。可选页面预读、跨回合来源缓存、后台摘要预生成还需分别设计身份、时效、版本和授权失效策略，不宜用未经核验的旧正文换速度。

**还发现一个与长尾等待有关的边界**

研究服务的 25 秒计时器只触发自身 controller 的 abort。`readResult` 调用 `gatewayFetch(result.url)` 时没有传研究 signal，公共读取也没有将该 signal 传到实际 fetch；部分等待要在返回后才检查超时。父回合和 Gateway 仍有自己的取消/上限，但“研究 25 秒”不是所有底层等待都能立即结束的硬上限。

正文并行改造前，应覆盖挂起的抓取、研究超时、主动停止、停止后重发和迟到结果，补齐信号及可取消等待。不能靠缩短常量或吞掉必要读取失败处理这个问题，也不能据此断言它就是本次一分钟的真实原因。

另有相邻兼容问题：Gateway 错误规范化后可能丢失 HTTP `status`，导致研究层按 404/405/501 触发的公共搜索回退不生效。它更偏向失败路径，应另建回归处理，不作为本次成功回答慢的归因。

**如何验证收益**

先使用已有诊断日志，将一次回合分为提交→准备结束、联网判断、搜索、每篇抓取、主模型请求→首思考、首正文、完成。相同请求在 Gateway 和 transport 层有重复记录，不能把两层 duration 相加。

对照应固定赛事/时间、问题、资料范围、回答长度和思考设置，分别记录“首个有用正文”和“完整回答”，至少覆盖原句、明确联网版、普通稳定知识、本页总结四类。优化前后用同一服务对比，多次重复记录中位数和慢请求；竞品的单次 8 秒只作为用户体验参照。概率输出还需检查赛事阶段、阵容/数据日期和不确定性，不能用省略事实核验取得速度。

现有日志已记录 first-byte、first-reasoning、first-content、请求用途和阶段耗时，见 [diagnostic-observer.js](../src/utils/diagnostic-observer.js) 与 [诊断日志说明](2026-11-06-diagnostics.md)。无需先搭新的遥测系统。尚未获得该次普通问答诊断，因此没有真实耗时分摊、服务端排队判断或优化后的秒数承诺。

现在即可使用的临时办法：不依赖当前网页时关闭“基于当前页”，保留联网检索；提问写成“联网分析 BLG 和 GEN 在【赛事、日期】的夺冠可能性与对位实力，先给简要结论”；对速度优先的回答可试低思考强度。明确联网能确定省掉当前分类调用，低思考是否有效取决于中转服务，且当前只影响主回答，不会自动修好辅助判断参数。
